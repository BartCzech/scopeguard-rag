# Abstract: Scope-Based Retrieval Architecture

As enterprises integrate Large Language Models (LLMs) with internal knowledge bases via Retrieval-Augmented Generation (RAG), traditional Role-Based Access Control (RBAC) proves insufficient. This whitepaper outlines the theoretical foundation and practical implementation of Scope-Based Retrieval Architecture, the core technology powering ScopeGuard AI.

### The Problem with Post-Retrieval Filtering
Standard RAG architectures execute a semantic similarity search across a vector database using an Approximate Nearest Neighbor (ANN) algorithm. If filtering happens *after* retrieval, or relies on LLM prompt instructions, the system is vulnerable to context window extraction attacks and prompt injection. 

### The Pre-Filter Imperative
To guarantee data security, authorization must be resolved before or during the vector search. ScopeGuard utilizes a dynamic pre-filtering engine. 

When documents are chunked and embedded, they are tagged with hierarchical scope metadata (e.g., `scope: ["engineering:internal", "project_apollo:core"]`). 

When a query is initiated:
1. The middleware intercepts the request and retrieves the user's cryptographically signed JSON Web Token (JWT) representing their current scopes.
2. The query is translated. Instead of a raw vector search, ScopeGuard constructs a compound query containing both the vector embedding of the prompt and a hard boolean filter matching the user's scopes.
3. The vector database (e.g., Pinecone) executes the ANN search *only* across the subset of vectors that satisfy the boolean scope filter.

### Performance Implications
Historically, metadata pre-filtering severely degraded the performance of ANN algorithms by fragmenting the graph or tree structures used for fast search. ScopeGuard addresses this by utilizing optimized indexing strategies and a proprietary caching layer that maps scope hierarchies in memory, ensuring that latency overhead remains under 50ms per query even in multi-tenant enterprise environments.
