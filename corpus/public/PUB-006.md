**By The ScopeGuard Security Research Team**

Much of the conversation around LLM security focuses on prompt injection—the act of tricking a model into ignoring its instructions through clever user inputs. But for enterprise Retrieval-Augmented Generation (RAG) systems, there is a much more insidious threat lurking beneath the surface: retrieval poisoning.

In a standard RAG architecture, an AI assistant answers questions by first querying a vector database for relevant documents. If an attacker can introduce a malicious document into that vector store—perhaps by uploading a seemingly innocuous resume to an HR portal or adding a hidden comment to a shared wiki—they can effectively lay a trap. 

When an unsuspecting employee later asks the AI a related question, the vector database retrieves the poisoned document. The malicious instructions embedded within it are fed directly into the LLM's context window, hijacking the assistant to exfiltrate data or generate harmful outputs. 

We recently simulated these attack vectors extensively, and as detailed in our internal security audit (SG-SEC-2024-07), relying solely on the LLM to sanitize retrieved context is highly unreliable. Once the poisoned data is in the context window, the model is already compromised.

The only reliable defense against retrieval poisoning is limiting the blast radius at the retrieval layer. By implementing strict, identity-based scope filtering with ScopeGuard, you ensure that even if a poisoned document exists in your corporate vector store, it can only be retrieved by the specific user or system that created it. If the HR team’s AI assistant queries the database, ScopeGuard’s middleware blocks the unauthorized, poisoned chunk from ever reaching the LLM, neutralizing the threat before it begins.
