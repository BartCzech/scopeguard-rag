# Post-Mortem: INC-2024-08-12

**Severity:** HIGH
**Impact:** During a live sales demo, the AI assistant surfaced test data belonging to another tenant.
**Duration:** 15 minutes (during the demo)

### Timeline (PST)
* **14:00** - Bart Check begins live demo with a major healthcare prospect.
* **14:12** - Bart queries the demo AI agent. The agent returns a response containing fake, but clearly labeled, financial data from a completely different demo tenant environment.
* **14:15** - Demo is paused. Bart flags the engineering team in Slack.
* **14:30** - Root cause identified in the shared staging vector index.

### Root Cause Analysis
The issue was caused by a misconfiguration in our multi-tenant embedding isolation for the staging environment. 
To save costs on our AWS bill, we consolidate demo data for different simulated companies into a single Pinecone index, relying on our own ScopeGuard middleware to enforce tenant isolation via the `tenant_id` scope flag. 

However, a recent PR introduced a bug in the JWT validation logic specifically for the `sales_demo` user role, which caused the `tenant_id` filter to be dropped from the query payload. The vector search defaulted to scanning the entire index, returning chunks from the wrong demo tenant. 

### Remediation & Action Items
1.  **Immediate:** Reverted the offending PR that broke the JWT validation. 
2.  **Process:** We can no longer rely on logical isolation for sales demos. We must use dedicated vector indices for different demo environments, mimicking our Enterprise tier architecture. (Assigned to DevOps).
3.  **Testing:** Add E2E regression tests specifically validating cross-tenant data leakage in shared environments.
