# ScopeGuard Brand & Style Guide (Docs)

When writing public-facing documentation, blog posts, or marketing materials, please adhere to the following guidelines to ensure a consistent voice.

### Tone & Voice
We are authoritative but accessible. We sell to highly technical engineering teams and risk-averse CISOs. 
* **Do:** Sound confident, precise, and mathematical.
* **Don't:** Use overly aggressive startup hype (e.g., "we are revolutionizing the space"). Let the technology speak for itself.
* **Core Tagline:** Always use "Your AI knows only what it should."

### Terminology Rules
* **ScopeGuard:** One word, capital S, capital G. Never "Scope Guard" or "Scopeguard". 
* **Middleware:** We are *middleware* or an *authorization layer*. We are NOT an LLM, a chatbot, or a database.
* **Pre-Filtering vs. Post-Filtering:** Always emphasize that we do *pre-retrieval filtering*. Contrast this with our competitors' inferior *post-retrieval filtering* (but do not name competitors like RivalShield in public docs).

### Formatting
* Use `inline code blocks` for API endpoints, JSON fields, and variable names.
* Bold key concepts on their first mention.
* When listing steps, use numbered lists. For features, use bullet points.

### Documenting Security Features
Because we are a security company, transparency is key. However, never expose internal architecture details (like our Redis caching strategy or specific AWS cluster names) in public support docs. Refer to them generally as our "high-performance caching layer."
