# Post-Mortem: Embedding Pipeline Outage

**Date:** October 18, 2024
**Severity:** MEDIUM
**Impact:** Background document indexing was halted for 2 hours. Customer queries (retrieval) were unaffected. 

### Timeline (PST)
* **09:15** - Alert triggered: SQS dead-letter queue for the embedding workers spiked above threshold. 
* **09:20** - DevOps identifies that all three active `g4dn.xlarge` GPU instances running our embedding models have crashed. 
* **09:30** - Auto-scaling group attempts to spin up new instances, but they crash within 2 minutes of joining the pool.
* **10:45** - The root cause is identified as an Out of Memory (OOM) error. The offending batch job is manually killed.
* **11:15** - Pipeline recovers and processes the backlog.

### Root Cause Analysis
A new Enterprise customer uploaded an exceptionally large, malformed PDF (a 600-page concatenated scan of financial reports) via the API without standard pagination. 

Our pre-processing chunker failed to split the document correctly due to missing whitespace characters in the OCR text. As a result, a massive 15,000-token chunk was sent directly to the Hugging Face embedding model. The model attempted to load the entire chunk into VRAM, causing an immediate OOM crash on the GPU worker. 

Because the job failed, SQS put the message back in the queue, causing the next worker to pick it up and crash, resulting in a continuous crash loop.

### Action Items
1. **Hard Limits:** Implement a strict token-length validation (max 512 tokens) *before* sending any payload to the embedding workers. Drop and log any chunks that exceed this. (Owner: Backend Team)
2. **Alerting:** Add specific Datadog alerts for GPU memory utilization spikes, rather than just relying on SQS queue depths. (Owner: DevOps)
