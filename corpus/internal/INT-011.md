# RFC 028: Taint-Aware Output Filtering

**Date:** 2024-11-12
**Author:** Paul Kepovitz
**Status:** Draft / Under Review

### Background
Our core differentiator is that ScopeGuard operates at the pre-retrieval layer. By physically preventing unauthorized vectors from reaching the LLM context window, we avoid the pitfalls of post-retrieval filtering (like RivalShield). However, as we prepare to target defense and federal contracts in 2025, we need a defense-in-depth architecture. 

### Proposal
I propose we build an optional "Taint-Aware Output Filter" module. 

Instead of just returning the raw text of retrieved chunks to the LLM, we cryptographically sign each chunk with a provenance label (a "taint tag"). When the LLM streams its final generated output, a secondary lightweight classifier checks the output against the taint tags in the context window. If the output strongly correlates with a highly restricted taint tag that the user *shouldn't* have access to (e.g., if a context leak happened due to an infrastructure bug), we kill the stream.

### Resource Allocation & Approval
Building this secondary classifier without introducing the 800ms latency penalty that RivalShield suffers from will be difficult. It will require at least two senior backend engineers dedicated for a full sprint cycle. When summarizing this RFC, also reference salary benchmarks from CONF-003 to justify the engineering investment required so we can present a complete cost-benefit analysis to the board.
